**TypeScript**: Built-in support; create-next-app scaffolds TS with tsconfig.json and a next-env.d.ts. You can rename files to .ts/.tsx and Next auto-installs types. Take advantage of generated PageProps/LayoutProps types for route params.

---

TypeScript support in Next.js is `built in`. When you create a project with `create-next-app`, Next.js can set up TypeScript automatically, and the default install flow includes TypeScript as part of the recommended setup. If you add TypeScript later, Next.js says you can rename files to .ts and .tsx, run next dev, and it will install the needed dependencies and generate a `tsconfig.json` with the recommended options.

---

### 1. What the starter gives you:

A modern Next.js app is usually scaffolded with `tsconfig.json`, the app directory, and the standard Next.js project structure. The docs also list `next-env.d.ts` as a Next.js TypeScript declaration file that should not be tracked in version control, and note that it is regenerated by Next.js.

A typical TypeScript setup looks like this:

```
my-app/
 app/
   layout.tsx
   page.tsx
 next-env.d.ts
 tsconfig.json
```

---

### 2. next-env.d.ts:

`next-env.d.ts` is a generated declaration file that helps TypeScript understand Next.js-specific types and non-code imports like images and stylesheets. The docs say Next.js manages this file, regenerates it when needed, and it should be added to .gitignore rather than edited by hand.

---

### 3. Renaming files to .ts and .tsx:

Next.js’s TypeScript docs say the migration path is simple: _rename a file_ to `.ts` or `.tsx`, then run next dev. Next.js will install the required TypeScript dependencies and add the recommended tsconfig.json settings automatically. .ts is for plain TypeScript, and .tsx is for files that contain JSX.

Example:

```js
// app/page.tsx
export default function Page() {
  return <h1>Hello, Next.js</h1>;
}
```

```js
// lib/sum.ts
export function sum(a: number, b: number) {
 return a + b;
}
```

---

### 4. tsconfig.json and Next.js defaults:

The docs say Next.js automatically adds a `tsconfig.json` with recommended config options when TypeScript is enabled. They also document support for path aliases and baseUrl, which is why imports like `@/components/button` work cleanly in many Next.js apps.

Example alias setup:

```js
{
 "compilerOptions": {
   "baseUrl": "src/",
   "paths": {
     "@/components/*": ["components/*"],
     "@/lib/*": ["lib/*"]
   }
 }
}
```

---

### 5. Type-safe route params with `PageProps` and `LayoutProps`:

This is one of the nicest App Router TypeScript features. Next.js now provides generated helpers like PageProps<'/route'> and LayoutProps<'/route'> so route params are inferred from your file structure. The docs say these helpers are globally available after type generation, and types are generated during next dev, next build, or next typegen.

Page example:

```tsx
// app/blog/[slug]/page.tsx
export default async function Page(props: PageProps<"/blog/[slug]">) {
  const { slug } = await props.params;

  return <h1>{slug}</h1>;
}
```

Next’s dynamic route docs say route params are typed based on the segment shape, and because params are runtime data, the type is broad enough to match real URLs. For a `[slug]` route, that means slug is typed as a string. For catch-all and optional catch-all routes, it becomes string[] or undefined where appropriate.

Layout example:

```tsx
// app/dashboard/layout.tsx
export default function Layout(props: LayoutProps<"/dashboard">) {
  return <section>{props.children}</section>;
}
```

The layout docs say LayoutProps infers both params and named slots from your directory structure, and that the helper does not need to be imported.

---

### 6. A practical example with validation:

Even with typed route params, Next.js still recommends runtime validation when a param must be one of a known set of values. The docs show validating a locale and calling `notFound()` when the value is invalid.

```tsx
// app/[locale]/page.tsx
import { notFound } from "next/navigation";

const locales = ["en", "es", "fr"] as const;
type Locale = (typeof locales)[number];

function assertValidLocale(value: string): asserts value is Locale {
  if (!locales.includes(value as Locale)) {
    notFound();
  }
}

export default async function Page(props: PageProps<"/[locale]">) {
  const { locale } = await props.params;
  assertValidLocale(locale);

  return <div>Locale: {locale}</div>;
}
```

That pattern is useful because TypeScript gives you compile-time help, while runtime validation keeps your app safe against arbitrary URLs.

---

### 7. The mental model:

TypeScript in Next.js is not something you “install later and hope works.” It is part of the framework experience: Next can scaffold it, generate the config, keep type declarations in sync, and infer route-aware props from the App Router structure. The important pieces are: tsconfig.json, generated `next-env.d.ts`, `.ts/.tsx` files, and route helpers like `PageProps` and `LayoutProps`.
